<objective>
Introduce the per-lift-per-program progression storage model that the Test-3 blocker fix depends on: a new `program_exercise_progress` table keyed by (program_id, exercise_id) carrying the lift's shared `working_weight_kg` + `consecutive_fails`. This is the storage contract Plan 06-08 reads and writes.

Purpose: Linear progression is currently keyed per-template-exercise-row (db/schema.ts `template_exercises.target_weight_kg` / `consecutive_fails`), so a lift that appears on two program days (StrongLifts A/B Squat) has two independent progression states — a Squat bump on Day A never reaches Day B. The approved fix (per-lift SHARED progression) requires a program-scoped, per-lift state row. This plan lands ONLY the additive schema + migration + safety test; Plan 06-08 moves the logic onto it.
Output: db/schema.ts table + types, an additive migration 0005 (generated), and a migration-safety test proving 0004 -> 0005 preserves data.
</objective>

  - `exerciseId` = int("exercise_id").notNull().references(() => exercises.id)
