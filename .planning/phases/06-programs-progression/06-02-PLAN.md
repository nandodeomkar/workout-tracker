## Phase Goal (MVP user story)

**As a** lifter, **I want to** run a structured multi-week program that advances through its days and auto-progresses my working weights, **so that** I can follow a proven plan without recalculating loads every session.

This plan is the data-foundation slice: the additive migration (origin marker + fail counter), the `db/programs.ts` data layer, and the two bundled-program JSON definitions. After this plan the engine is exercisable end-to-end in tests (add a bundled program → start a day → distinguish origin), even though the UI to do it lands in Plan 03.

<objective>
Add the two additive columns Phase 6 needs (program origin marker on `workouts`, consecutive-fail counter on `template_exercises`), generate the bundled migration `0004`, and build `db/programs.ts` — the transactional, driver-agnostic program data layer that mirrors `db/templates.ts`. Ship the two bundled-program JSON definitions (D-14) as static data materialized into user-owned rows (D-15), never seeded into the DB.

Purpose: Everything downstream (home card, program detail, finish-flow progression, custom builder) sits on this layer. Getting the origin marker (D-05) and clone-not-mutate (D-15) right here is what keeps progression writes safe and ad-hoc reuse from corrupting a program.
Output: migration 0004 + `db/programs.ts` + `db/programs.crud.test.ts` (green) + `data/bundledPrograms/*`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bundled JSON (app asset) → DB rows | Static bundle definitions crossing into user-owned DB rows during materialization |
| stored `template_exercises.progression` free-text JSON → math | A free-text column parsed and used by progression math |
| numeric inputs (increment_kg, training max, day position) → SQLite writes | Untrusted numeric values reaching parameterized writes |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-02 | Tampering / DoS | program_days.position / current_day_position | mitigate | assertValidDayPosition (integer, >=0) on writes; pointer advance always via `(pos+1) % dayCount` in Plan 04, never a stored index trusted against a stale dayCount. |
| T-06-03 | Tampering | increment_kg, training_maxes.max_kg, consecutive_fails writes | mitigate | assertValidIncrementKg / assertValidTrainingMaxKg / assertValidConsecutiveFails reject NaN/negative/non-finite/absurd before every insert/update (ASVS V5), mirroring db/templates.ts. |
| T-06-04 | Tampering | all db/programs.ts queries | mitigate | Drizzle parameterized query-builder only; no string-concatenated SQL (codebase-wide convention). |
| T-06-05 | Tampering | missing/renamed bundle seed_id | mitigate | Resolve every bundle exercise seed_id to a real exercises.id up front; THROW a clear error rather than insert a dangling/null exercise reference (Pitfall 6). |
| T-06-06 | Tampering | shared bundle JSON mutation | mitigate | Bundle typed as BundledProgramDefinition (distinct from Program/Template rows); materialization only ever inserts fresh rows and never writes back to the bundle object (Pitfall 4); clone-independence test proves two adds are non-shared. |
| T-06-SC | Supply chain | package installs | accept | No package installs this phase (06-RESEARCH.md Package Legitimacy Audit = N/A). |
</threat_model>
