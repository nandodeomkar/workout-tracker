<objective>
Prove STAT-04: the stats layer stays responsive against years of history. This plan generates a deliberately-generous synthetic dataset (~5 years, ~780 workouts, ~15,600 sets) in the existing in-memory better-sqlite3 fixture and times the three query paths built in Plans 02-04, asserting a conservative regression ceiling. It also gates on a manual on-device pass, because the Node timing only proves the data-layer half — chart *rendering* frame time (Skia GPU) is not automatable in this project's Node-only vitest strategy, and that gap is called out explicitly rather than over-claimed.

Purpose: Turn "charts stay responsive with years of history" from an aspiration into a timed regression guard plus a documented device check.
Output: `db/test/syntheticHistory.ts` (seed generator), `db/stats.performance.test.ts` (timed assertions), and an on-device verification checkpoint.

This plan modifies NO production code and does NOT touch `db/schema.ts` — per the STAT-04 strategy (RESEARCH.md), per-workout/per-week aggregation happens in JS after a targeted fetch, and the ~15,600-row scan is expected in low tens of ms with the existing indexes; no new index or `drizzle-kit push` is required. (If, and only if, the timed assertion fails and profiling shows a genuine index need, that becomes a follow-up gap-closure plan that would then own the schema change + push gate — not this plan.)
</objective>
