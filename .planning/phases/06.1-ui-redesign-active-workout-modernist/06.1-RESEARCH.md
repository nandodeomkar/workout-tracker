# Phase 06.1: UI Redesign — Active Workout (Modernist) - Research

**Researched:** 2026-07-24
**Domain:** React Native (Expo SDK 57 / RN 0.86 / New Architecture) UI re-skin + two-mode presentation layer over an existing SQLite-backed logging engine
**Confidence:** HIGH

## Summary

This phase is **not** a rewrite: every behavior the redesign needs (crash-safe checkmark logging, rest timer, keypad, calculators, drag-reorder, add/replace/remove exercise, discard/finish) already exists in `app/active-workout/[workoutId].tsx` (1277 lines) and its six mounted child components. The work is (1) a global `theme.ts` token revalue that 47 files import, (2) a structural rebuild of one screen's JSX/styles to the Modernist visual language, and (3) three new npm dependencies that have zero precedent in this codebase (font loading, SVG, and a new icon library) plus reanimated keyframe-style animations that also have zero precedent (the codebase's only current reanimated use is `ExerciseCard`'s drag-and-drop spring, not sequenced/repeated animations).

The single most consequential correction to the CONTEXT.md/UI-SPEC assumption: **`react-native-svg` is NOT installed, transitively or otherwise.** `victory-native@41.26.0` is a from-scratch Skia renderer with dependencies `d3-scale`/`d3-shape`/`d3-zoom`/`its-fine`/`react-fast-compare` — it does not touch `react-native-svg` at all. The planner must add `react-native-svg` as a new **direct** dependency, not assume it. `lucide-react-native` and `@expo-google-fonts/archivo` are also both fully absent — all three are genuinely new installs.

The exercise-menu sheet the UI-SPEC specifies is **not a restyle of an existing sheet** — it's a new component. Today, Replace/Remove live in an `Alert.alert` action sheet (`handleOverflowPress`, line 827), and Plate/1RM/Warm-up are three separate header icon buttons on `ExerciseCard` (`onOpenPlateCalculator`/`onOpenOneRM`/`onOpenWarmup`, lines 136-165). The UI-SPEC's "Menu decision" (§6) correctly identifies this consolidation is required — the planner should treat the exercise-menu sheet as new code, not a chrome-only restyle, and must wire it to five existing handlers/openers rather than one.

**Primary recommendation:** Revalue `theme.ts` first (fastest, highest blast-radius, easiest to regression-check via the 47 consuming files still compiling), then land the three new deps + font-gate in `app/_layout.tsx` as an isolated step (reuses the screen's *existing* `!success || !seeded → return null` gating pattern — no `expo-splash-screen` needed), then rebuild the active-workout screen's JSX in place, preserving every handler signature and component prop boundary documented below.

| Property | Value |

**Usage pattern** (extends the app's existing render-gate — do NOT add `expo-splash-screen`, it is not currently used):

```tsx
// app/_layout.tsx — current gate (line 41-43):
//   if (!success || !seeded) { return null; }
// Extend with fontsLoaded:
import { useFonts, Archivo_400Regular, Archivo_600SemiBold, Archivo_700Bold, Archivo_800ExtraBold } from '@expo-google-fonts/archivo';

const [fontsLoaded] = useFonts({
  Archivo_400Regular,
  Archivo_600SemiBold,
  Archivo_700Bold,
  Archivo_800ExtraBold,
});

// ... existing useMigrations/seed logic unchanged ...

  return null;
}
```

**Gotchas:**
- RN applies custom fonts **by family name**, not by numeric `fontWeight` — each loaded font is registered under its literal export name (e.g. `'Archivo_800ExtraBold'`), so `theme.typography.*` entries must set `fontFamily: 'Archivo_800ExtraBold'` (a string, not `'Archivo'` + `fontWeight: 800`). `fontWeight` in the style object becomes cosmetic (useful only as an Android font-fallback hint before load finishes) — this matches CONTEXT.md/UI-SPEC's own statement, now confirmed against Expo's actual font-registration mechanism.
- The existing gate pattern (`return null` while loading) means a font-load in-progress state is invisible — no blank flash beyond what already happens during migration/seed. No New Architecture caveats: `expo-font`'s `useFonts` hook is Fabric-compatible and unchanged from its Old Architecture behavior.
- Because `app/_layout.tsx` already imports `theme` and uses `theme.typography.title/body` inline (lines 102, 107), the font-family strings must exist in `theme.ts` BEFORE this hook is wired, or fall back gracefully — sequence the theme.ts token rewrite before the `_layout.tsx` font-gate edit.

**Minimal sparkline pattern** (76×26 per-exercise sparkline, pure `react-native-svg`, not Skia — cheap for a small per-card decoration, matches UI-SPEC's explicit "SVG 76×26" spec):

```tsx
import Svg, { Polyline, Line } from 'react-native-svg';

// points: number[] — last 8 best-e1RM values from buildChartSeries(...).map(p => p.value)
function Sparkline({ points, color }: { points: number[]; color: string }) {
  const W = 76, H = 26;
  if (points.length === 0) {
    // no-history: flat mid-height line, per UI-SPEC §3b
    return (
      <Svg width={W} height={H}>
        <Line x1={0} y1={H / 2} x2={W} y2={H / 2} stroke="#7d7979" strokeWidth={1.6} />
      </Svg>
    );
  }
  const min = Math.min(...points);
  const max = Math.max(...points);
  const range = max - min || 1;
  const step = points.length > 1 ? W / (points.length - 1) : 0;
  const coords = points
    .map((v, i) => `${i * step},${H - ((v - min) / range) * H}`)
    .join(' ');
  return (
    <Svg width={W} height={H}>
      {/* baseline rule per UI-SPEC: rgba(245,242,239,.14) */}
      <Line x1={0} y1={H} x2={W} y2={H} stroke="rgba(245,242,239,0.14)" strokeWidth={1} />
      <Polyline points={coords} fill="none" stroke={color} strokeWidth={1.6} />
    </Svg>
  );
}
```

`<Polyline>`'s `points` prop takes a space-separated `"x,y x,y ..."` string; `viewBox` is not required when `width`/`height` are set directly on `<Svg>` and the coordinate math is done in the same unit space `[CITED: react-native-svg USAGE.md, github.com/software-mansion/react-native-svg]`.

**Gotchas:**
- No Babel/Metro config change needed for this usage pattern (no `.svg` file imports, only JS components).
- Rendering 3-6 small SVGs (one per exercise card) per screen is cheap; do not use Skia for this — UI-SPEC explicitly calls this out ("cheap") and victory-native's Skia canvas is reserved for the Stats-tab charts, not this screen.

### A4. Reanimated keyframe-equivalent animations (reanimated 4.5.0 installed, worklets 0.10.0)

This codebase's only current reanimated usage is `ExerciseCard`'s drag gesture (`useSharedValue` + `withSpring`, lines 85-117 of `components/ExerciseCard.tsx`) — no existing precedent for `withRepeat`/`withSequence`/looping animations. All patterns below are standard reanimated 3/4 API, unchanged across the v3→v4 New Architecture migration `[CITED: react-native-reanimated official docs — stable API since v2]`.

**`prflash`** (PR star: opacity 0.95↔0.4, 1.6s ease-in-out, infinite):
```tsx
import Animated, { useSharedValue, useAnimatedStyle, withRepeat, withTiming, Easing } from 'react-native-reanimated';

const flash = useSharedValue(0.95);
useEffect(() => {
  flash.value = withRepeat(
    withTiming(0.4, { duration: 1600, easing: Easing.inOut(Easing.ease) }),
    -1, // infinite
    true, // reverse (yoyo) — gives the 0.95↔0.4 ping-pong from one withTiming call
  );
}, []);
const starStyle = useAnimatedStyle(() => ({ opacity: flash.value }));
```

**`restpulse`** (rest countdown: opacity 1↔0.5, 2s, infinite) — identical pattern, `withTiming(0.5, { duration: 2000 })`, `withRepeat(..., -1, true)`.

**`sheetup`** (sheet entrance: translateY 30→0 + opacity .4→1, ~180ms, one-shot, not repeated):
```tsx
const translateY = useSharedValue(30);
const opacity = useSharedValue(0.4);
useEffect(() => {
  translateY.value = withTiming(0, { duration: 180, easing: Easing.out(Easing.ease) });
  opacity.value = withTiming(1, { duration: 180 });
}, []);
const sheetStyle = useAnimatedStyle(() => ({
  transform: [{ translateY: translateY.value }],
  opacity: opacity.value,
}));
```

**Reduce-motion:** RN's `AccessibilityInfo.isReduceMotionEnabled()` (core RN API, not reanimated-specific) can gate whether `withRepeat`/`withTiming` durations collapse to `0` — trivial to wire (`const reduceMotion = await AccessibilityInfo.isReduceMotionEnabled()` once, gate the animated-value assignment) but UI-SPEC marks this "if trivial", so treat as nice-to-have, not blocking.

**Gotchas:**
- All three animated components (PR star, rest countdown, sheet) must call `useSharedValue`/`useAnimatedStyle` unconditionally at the top of their component (rules-of-hooks) — do not attempt to start these animations inside a conditional render branch; instead gate the *visibility* of the wrapping component (existing `visible` prop pattern already used by `NumericKeypad`, `PlateCalculatorSheet`, etc.) while the animated style itself is always computed.
- `react-native-worklets@0.10.0` (already installed) is the reanimated 4 dependency split-out — no separate install needed; it's already satisfied.

## Common Pitfalls

### Pitfall 1: Assuming `react-native-svg` is already satisfied transitively
**What goes wrong:** Skipping the explicit `npm install react-native-svg` because victory-native/Skia "probably" provides it, then hitting an unresolved-module crash the first time `lucide-react-native` or the sparkline component renders.
**Why it happens:** Skia and SVG are both "vector graphics" libraries so it's an easy but incorrect mental leap; victory-native's docs/README don't loudly advertise that it's Skia-only.
**How to avoid:** `npm ls react-native-svg` before writing any icon/sparkline code; this research already confirms it returns empty in this repo as of 2026-07-24.
**Warning signs:** Metro bundler error "Unable to resolve module react-native-svg" the first time any lucide icon or the sparkline component is imported.

### Pitfall 2: Treating the exercise-menu sheet as a pure chrome restyle
**What goes wrong:** Scoping a plan task as "restyle the exercise overflow menu" when it actually needs to consolidate five separate existing entry points (Alert-based Replace/Remove + three header icon buttons) into one new sheet component with new routing logic.
**Why it happens:** The UI-SPEC's phrasing ("Exercise menu sheet (restyle...)") reads like the other sheet restyles (Plate/1RM/Warmup calculators), but unlike those three, this one's *trigger surface* is being restructured, not just its *chrome*.
**How to avoid:** Scope this as new-component work with five wiring points, sized accordingly, not lumped in with the three calculator sheets' one-line chrome-only restyles.

### Pitfall 3: Losing the `onLayout` wrapper View around each exercise card
**What goes wrong:** During the JSX rebuild, the outer `<View key={entry.weId} onLayout={...}>` wrapper (lines 995-1000) gets collapsed into the new card component's own root view, silently breaking drag-reorder because `cardLayoutsRef` never gets populated.
**Why it happens:** It looks like redundant nesting when redesigning a component's internal structure.
**How to avoid:** Keep the screen-level `onLayout` measurement wrapper exactly where it is; only the JSX *inside* `<ExerciseCard>` should change.
**Warning signs:** Drag-reorder gesture completes (spring animation plays) but the exercise order never actually changes.

// Working (non-warmup) sets only, across ALL cards' logged rows:
function computeSessionVolumeKg(rowsByWE: Record<number, Row[]>): number {
  return Object.values(rowsByWE)
    .flat()
    .filter((r) => r.isCompleted && !r.isWarmup)

All eight of CONTEXT.md's open questions (OQ-1 through OQ-8) are resolved in `06.1-UI-SPEC.md` (approved 2026-07-24, checker sign-off 6/6). No new open questions were surfaced by this research beyond the two explicit planner-decision points called out in Landmines #3 and #7 (exercise-menu sheet scope, `RestTimerBar` idle-state prop contract) — both are implementation-detail decisions, not open product questions, and this research recommends a specific direction for each:

1. **Exercise-menu sheet component boundary**
   - What we know: it must replace `handleOverflowPress`'s Alert and absorb three `ExerciseCard` header buttons.
   - What's unclear: whether it's a new top-level component mounted once at screen level (like the existing calculator sheets) or a component owned by `ExerciseCard`.
   - Recommendation: mount it once at screen level, mirroring the existing `openSheet` state pattern (`{kind, weId, rowKey} | null`, lines 168-172) — add `'menu'` as a fourth `kind`, so all four sheets (menu + 3 calculators) share one `openSheet`/`closeSheet` state machine instead of a fifth ad-hoc state variable.

2. **`RestTimerBar` idle-state prop contract**
   - What we know: UI-SPEC wants a persistent idle visual whenever `restEndsAt == null`.
   - What's unclear: whether `RestTimerBar` itself grows an "idle" render branch (new prop, e.g. making `restEndsAt` nullable on the component itself instead of conditionally mounting it) or a new sibling component handles idle-only.
   - Recommendation: make `RestTimerBar` always-mounted with `restEndsAt: number | null` (widen the existing prop type) and an internal branch — keeps one component, one file, avoids a second nearly-identical idle-only component, and the screen's render logic simplifies from a ternary-mount to always rendering `<RestTimerBar restEndsAt={restEndsAt} .../>`.
