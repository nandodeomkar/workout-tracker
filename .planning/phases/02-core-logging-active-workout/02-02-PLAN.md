## Phase Goal (user story)

**As a** lifter training in the gym, **I want to** log every set of my workout in a couple of taps and have it saved the instant I tap ✓, **so that** logging is fast, works offline, and never loses data even if the app crashes or my phone restarts.

> This plan builds the crash-safe data core — the heart of LOG-02. It proves at the DB-test layer that a set written on ✓ survives a simulated crash (a fresh DB connection re-reads it) and that an unfinished workout resumes. The UI (Plan 04) renders this layer; the guarantee lives here.

<objective>
Add the per-exercise rest-override column (D-08) via one additive Drizzle migration following the FNDN-02 precedent, then build the crash-safe workout/set data layer (`db/workouts.ts`) and the key-value settings helper (`db/settings.ts`), each with better-sqlite3 in-memory vitest coverage. This is the write/resume/pre-fill core of the logging loop; exercise mutations, discard/finish, and history queries follow in Plan 03.

Purpose: D-15 makes SQLite the sole source of truth — crash safety is a DB-layer property, not a UI one. Proving `insertSet` + `findResumableWorkout` + `loadLastPerformance` at the vitest layer (fresh in-memory DB = simulated crash) is how LOG-02 is verified without a device.
Output: migrated schema (`exercises.rest_seconds`), generated migration `0002`, an extended migration-safety test, `db/workouts.ts` (session-write core), `db/settings.ts`, and their tests — all green.
</objective>
