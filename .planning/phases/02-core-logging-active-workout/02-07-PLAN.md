## Phase Goal (user story)

**As a** lifter training in the gym, **I want to** log every set of my workout in a couple of taps and have it saved the instant I tap ✓, **so that** logging is fast, works offline, and never loses data even if the app crashes or my phone restarts.

> This final slice makes past work visible and reusable: a History tab (list + calendar), read-only workout detail, full editing of any past workout by reusing the logging screen (HIST-02/D-13), and the second start path — "Start from history" (D-04/D-05). It renders the Plan 03 history queries and reuses the Plan 04-06 active-workout screen for edit mode.

<objective>
Build the History tab and its detail/edit flow plus the "Start from history" entry. Convert the single-file `history` tab into a Stack route group (list + calendar toggle, workout detail, Edit reopening the active-workout screen in editing mode), add the `WorkoutRow` and custom `MonthCalendar` components (no new dependency), and wire the Workout-tab "Start from history" picker that copies a past workout's exercise list and pre-fills from each exercise's most recent performance (D-05/D-06).

Purpose: HIST-01/HIST-02 make the app a durable training log, not just a live logger; "Start from history" is the D-04 second start path that depends on history existing. Editing reuses the active-workout screen (D-13, one consistent UI) with the `mode='editing'` branch built in Plan 04 and rest-timer suppression from Plan 06.
Output: `app/(tabs)/history/_layout.tsx` + `index.tsx` + `[workoutId].tsx` (replacing `history.tsx`), `components/WorkoutRow.tsx` + `MonthCalendar.tsx`, and the "Start from history" addition to `app/(tabs)/index.tsx`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Edit CTA → active-workout editing mode | Editing a finished workout writes updates back to already-committed rows. |
| calendar/month inputs → loadWorkoutsInMonth | Year/month values drive a DB range query. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-17 | Tampering (data integrity) | edit mode ✓/number change | mitigate | The `mode='editing'` branch (Plan 04) calls `updateSet` on existing rows, never `insertSet` — prevents duplicate `(workout_exercise_id, set_number)` rows (Pitfall 1). Field edits write on change/blur so a mid-edit kill loses at most the last keystroke. |
| T-02-18 | Tampering | `loadWorkoutsInMonth` date bounds | mitigate | Month range bounds are computed in JS and passed as query parameters (Plan 03) — no string interpolation. |
| T-02-19 | Information Disclosure | none | accept | Single-user local app; history reads expose only the owner's own data, no cross-user boundary. |
</threat_model>
