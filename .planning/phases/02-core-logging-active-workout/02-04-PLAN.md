## Phase Goal (user story)

**As a** lifter training in the gym, **I want to** log every set of my workout in a couple of taps and have it saved the instant I tap ✓, **so that** logging is fast, works offline, and never loses data even if the app crashes or my phone restarts.

> This is the first user-demonstrable slice: after this plan a lifter can open the app, tap Start empty workout, add an exercise, and log sets with one ✓ tap — each write hitting SQLite immediately, and a killed app resuming the session. It renders the Plan 02 crash-safe data core and the Plan 01 kg/lb converter. Rich exercise management (reorder/replace/remove), the rest timer, finish/summary, and history land in Plans 05-07.

<objective>
Build the core logging loop UI: the Zustand session store (non-persisted, SQLite is source of truth per D-15), the full-screen active-workout route mounted as a sibling over the tabs, the set-entry components (steppers + custom numeric keypad + ✓ log button), and the Workout-tab entry (start empty / resume). Delivers LOG-01 (≤2-tap logging, pre-filled), LOG-02 (immediate persist + resume), and LOG-06 (kg/lb display) end-to-end in the running app.

Purpose: This is the app's entire reason to exist — the fast in-gym logging loop. It consumes the tested data layer (Plan 02) and pure converters (Plan 01) so the screen is thin glue over proven logic.
Output: `store/activeWorkout.ts`, `app/active-workout/_layout.tsx` + `[workoutId].tsx`, rewritten `app/(tabs)/index.tsx`, `components/SetRow.tsx` + `NumericKeypad.tsx` + `ExerciseCard.tsx`, plus the root route registration and the zustand dependency.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| keypad/steppers → insertSet | Untrusted numeric weight/reps entered on-screen crosses into the DB write via the ✓ handler. |
| Zustand session state ↔ SQLite | The store mirrors DB state for render; divergence (e.g. persisting the store) would create a second source of truth. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-09 | Tampering | ✓ handler → `insertSet` | mitigate | Numeric input is bounds-checked at the DB boundary by `assertValidWeightKg`/`assertValidReps` (Plan 02); the keypad only accepts digits/decimal, and `displayToKg` normalizes to canonical kg. |
| T-02-10 | Repudiation / data loss | active session vs store | mitigate | Store is non-persisted; every ✓ writes to SQLite immediately (D-15), and resume rehydrates from `findResumableWorkout` — the store is never the source of truth, so killing the app loses at most the last un-✓'d keystroke. |
| T-02-11 | Denial of Service (local UX) | set-write failure | accept | On insert failure the `notify()` toast surfaces "Couldn't save that set…"; logging is never blocked by a transient write error (the row simply stays un-completed for retry). |
</threat_model>
